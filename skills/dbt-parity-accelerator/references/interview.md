# Interview

Ask in this order. Every question has a default from the discovery summary the customer confirmed
(SKILL.md Step 1.5), including their corrections and exclusions; state it and the reason.
Write each answer into `deployment.yml` immediately. Field names refer to `MANIFEST.md`.

## Block A: Source control and auth  (`git.*`)

1. **"Which git provider hosts this repo, and is it already connected to this project?"**
   Default: from `git_remote` in the scan. Options: GitHub, GitLab, Azure DevOps.
   -> `git.provider`, `git.repo`.
2. **"Can pipelines authenticate with OIDC (workload identity, no stored secrets)?"**
   GitHub and GitLab: recommend OIDC. Azure DevOps: key pair (explain that OIDC to Snowflake
   from Azure DevOps was not verified for this accelerator, so the private keys are stored as
   pipeline secrets). Self-managed GitLab or GitHub Enterprise -> ask for the issuer URL.
   -> `git.ci_auth`, `git.oidc_issuer`.
   GitLab: merge-request pipelines need a custom `sub` claim for the CI user -> `git.ci_subject`.

## Block B: The dbt project  (`dbt.*`)

3. **"Is this the dbt project to deploy?"** List every `dbt_project.yml` the scan found.
   Monorepo with several projects: run the accelerator once per project, one manifest each,
   with distinct `object_name`s; pipelines are filtered by `project_dir`.
   No project yet -> load `dbt-projects-on-snowflake` ONBOARD, then come back.
4. **"Is it already deployed as a dbt project object?"** Show D3 results.
   - Yes: reuse `object_name` and its schema as `object_schema`. Record `dbt_version` as `runtime`.
     Do not offer a version change.
   - Runs today in dbt Core/Cloud/local: load `dbt-projects-on-snowflake` **MIGRATE** for profile
     and packages readiness, then come back. Its decisions feed `dbt.*` and `packages.*`.
5. Profile file: if the scan shows an in-project `profiles.yml` and no `dbt_projects_profiles.yml`,
   follow `dbt-projects-on-snowflake` PROFILES (its rename-suggestion policy). The accelerator
   always renders `dbt_projects_profiles.yml`.
6. `env_var()` keys: for each key in `env_var_calls`:
   - `DBT_SCHEMA` is generated by the accelerator.
   - Other `DBT_*` keys -> ask the per-environment value -> `dbt.extra_env_vars`.
   - Keys **without** the `DBT_` prefix: explain they won't resolve on Snowflake; propose renaming
     to `DBT_<UPPER>` in every reference (listed by the scan) following ENVIRONMENT. Never `var()`.
     Secret values -> Snowflake SECRET via ENVIRONMENT, never a literal in env.yml.
7. Packages -> `packages.needs_eai: true`. If an EAI for dbt deps already exists (D11), reuse its name.

## Block C: Environments  (`environments[]`)

8. **"How many environments do you want?"** Recommend dev -> qa -> prod. Accept 2..N
   (e.g. dev/test/uat/prod). Order matters: it's the promotion path.
9. Per environment: **branch**, **database** (adopt one from D4 or create), **schema** for the
   object and shared builds (`dbt.object_schema`, the same in every env), **build role**, optional
   **read-only role** for humans (recommend one on prod, so humans can't write prod).
   - Database owned by a role the admin can't use (e.g. ACCOUNTADMIN) -> set `owner_role`, and say
     that batch 10 will need that role for that one database.
   - Names: `target` and `env_yml_env` default to the environment name. If the project already has
     targets/env.yml envs, map to the existing names instead. `render.py` rejects ambiguous pairs.
10. `per_user_schema` for dev (recommended: interactive runs build into `DBT_<user>`).

## Block D: Roles  (`*.role`, `admin_roles`, `ci.role`)

11. **"What's your current role structure? Can we reuse it?"** Show D6/D7 candidates. Three paths:
    - **Adopt**: map existing functional roles to each environment's build role (`adopt: true`).
      Batch 20 only adds missing grants. Show the grants it would add.
    - **Extend**: create dbt-specific roles and grant them into their hierarchy under
      `admin_roles.objects` (default SYSADMIN).
    - **Greenfield**: create everything.
    Draw the resulting hierarchy (mermaid) and get confirmation before moving on.
    For a redesign, load the `rbac` skill.
12. Admin roles: who creates objects (`admin_roles.objects`) and who creates roles/users/grants
    (`admin_roles.security`, must hold MANAGE GRANTS per D8).
13. Service users: copy every user name from D9 into `discovered.service_users`. If the default
    prefix collides (another pipeline already uses it), propose a project-specific prefix such as
    `SVC_GH_<PROJECT>_`.

## Block E: Compute and sources

14. Warehouse: adopt from D5 or create (`warehouse.size`, recommend XSMALL to start; resize after
    observing build times). One shared warehouse is the default.
15. Sources: from `source_databases` in the scan. Per database: schemas to read
    (`sources[].schemas`), or `shared: true` for shares/Marketplace (needs the owner role).

## Block F: CI behavior  (`ci.*`, `schedule.*`)

16. Slim CI on PRs (recommend yes). Which environments host PR builds (`hosts_ci`; recommend the
    lowest env, plus each intermediate env so env-to-env PRs build in their own database).
    PR schema prefix, CI role name, PR cleanup (recommend yes).
17. Branch protection: requiring the `slim-ci` check needs a paid plan for private GitHub repos.
18. Optional scheduled run (e.g. nightly prod) in addition to deploy-on-merge -> `schedule.*`;
    follow `dbt-projects-on-snowflake` SCHEDULE.
19. **"Who will run the admin SQL?"** If not the current user, the outcome of Apply is exported
    scripts plus a hand-off note, not execution.

## Done when
`render.py deployment.yml --check` passes and the user has confirmed the summary:
environments table, role hierarchy diagram, list of objects to create vs adopt, and the pipeline
files that will be added or replaced.
